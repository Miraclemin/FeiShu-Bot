# 研发需求交接
## 配置入口（所有模式先读）
先读 [当前任务的配置与身份约定](references/context.md)，再按本次意图执行。桌面软件注入的 `<workbench_group_context>` / `Group project data:` 优先；不要重复 /project 绑定。
只查表时，直接以当前机器人身份识别已绑定资料并只读查询，不运行旧绑定、计划、巡检或发布脚本。项目名称、源码目录等非查询必需字段为空，不得报告整个群“未绑定”。
以下业务规则继续适用；固定脚本、路径、群/表/身份示例仅适用于 context.md 规定的旧流程。

需求表坐标从上述当前群研发profile绑定的requirements_url读取；桌面明确处理原OctoLead项目时使用codex与已配置研发群的绑定。使用本机lark-base技能及当前研发机器人身份读取，不调用强制product-manager身份的运行脚本。软件群项目取 workspace；旧流程示例项目 `<PROJECT_ROOT>`，先读AGENTS.md并保留所有无关WIP。

## 执行入口
完整读取 [优先级、并发与发布流程](references/workflow.md)。桌面群任务通过当前身份的 lark-base 实时筛选；仅旧流程使用 requirements_dev/plan.py 筛选；按高→中→低处理已批准且未开发需求。待评审不自动批准，开发中/待验收不重复开发。

每批最多5个子Agent，按实际槽位降低；独立worktree、主Agent独占认领与统一集成、组合验收。整批形成可审阅结果后统一问用户是否上线；拒绝则留存待验收成果，新需求进入下一批。

状态沿用已批准→开发中→待验收→已上线；研发任务与回执记录阶段、任务、提交、证据和阻塞。新增是否解决仅在用户批准、生产上线且对应验收通过后勾选。没有上线或尚未验证不标解决；已上线待验证的下次仅验收。

产出必须区分代码完成、已上线、已解决、受阻；最后给准确集成SHA和一次上线确认。遵守现有统一发布/回滚机制，不让子Agent各自上线。

上线验收后必须回写并核对已上线/是否解决，按workflow人员回执规则由飞书原生自动化通知需求提出人；开发人变更也由原生自动化通知，不调用轮询脚本。
