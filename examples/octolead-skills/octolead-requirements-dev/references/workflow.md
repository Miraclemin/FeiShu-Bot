# 按优先级批量开发需求

> 先遵守 [配置与身份约定](context.md)。软件群任务使用注入配置和当前机器人；本页固定脚本、路径、群/表及身份仅是旧流程示例。只读查询不执行写入或调度流程。

## 1. 读取与冻结批次

软件群先核对当前注入资料及实际需求表字段，使用当前机器人身份的 lark-base；代码实施才读取项目 AGENTS.md。旧流程的研发 profile 才是 codex。工具目录为 `<TOOLS_ROOT>`。

仅旧流程执行 `python3 requirements_dev/plan.py` 读取原OctoLead桌面绑定；群内传消息信封真实 `--chat-id`，Topic另传 `--topic-id`。脚本使用研发bot身份，不调用产品经理强制身份脚本。它只读表和生成本地读取材料，不自动认领或开发。

默认开工候选：是否解决不为true、状态已批准、必要验收材料完整、没有未核对的开发人/认领。优先级高→中→低，同级按创建时间→record_id稳定排序；未填优先级排末尾并说明。待评审、空白、待补充、暂缓、不采纳不自动开工；开发中先核对现有任务；待验收复用已有代码，不从头开发；已上线但未勾解决进入线上验收队列，不重新开发。

用户直接明确要求实现某条/一组需求，可作为这组需求的开发授权，不机械要求再点表格批准。在研发任务与回执记录授权出处与批准者后重读；本Skill的搭建或泛问流程不等于批准表里所有需求。无法取得人员ID就说明，不造开发人。已有开发人并非永远不处理，主Agent须核对是否本人任务及是否已有人执行，再决定认领/续接。

本次只冻结当时获准且可实施的record_id、优先级、需求指纹（场景/结果/验收）、依赖和基线SHA到manifest。新增需求留下一批；优先级不允许跳过前置依赖。尚待批准项单独报告，不阻断已获准且独立的需求。

## 2. 认领与并发

用户调用本Skill处理多个独立需求时，允许主Agent调用子Agent并行。每批最多5个子Agent，实际取min(5,可用槽位,独立候选数)；当前总4槽含主Agent时最多3个。整批结束并集成验证后才开下一批，不在同一代码目录并发修改。

主Agent串行操作Git、飞书和认领账本。使用工具目录 `requirements_dev/artifacts/claims.json` 与 `claims.lock`；通过Python fcntl排他锁完成“检查无活动认领→持久化认领及批次manifest”的同一临界区，临时文件原子替换。认领键为base_token/table_id/record_id，不能只用标题或批次名。manifest存于同目录各批次子目录，保存profile、群/Topic、项目路径、基线/集成SHA、ordered_record_ids、只前进的游标、各项状态和真实Agent任务ID。

账本是本机跨批次互斥，不是跨电脑原子锁。跨电脑仍需核对飞书开发人和实际任务；发现已有/未知认领停止该项，不覆盖、不按时间自动抢占。认领脚本尚无统一CLI，主Agent按上述协议使用本机Python文件锁编排；不能把plan.py称为原子认领工具。

每次派发前实时读原行，确认未解决、批准仍有效、需求指纹未改变且无他人活动任务。锁内完成认领后，先写表开发中和研发任务与回执（批次、真实开发人、分支、工位、阶段），成功后才派发；写入失败/超时先核对远端，不重复开工。

每项一个隔离worktree和 `codex/requirements-...` 分支，由主Agent串行创建后分给子Agent。子Agent只实现、测试、提交本项，不改表、不合并、不推送、不部署、不删其他worktree。不另设20分钟开发硬限制；巡检20分钟预算不套到需求研发。

改同一模块、依赖相同迁移或存在强交互的需求按依赖串行；并行先处理独立高优先级项。高优先级受阻可继续其他独立项，并写原因。不能把文本冲突自动解决当作语义正确。

## 3. 进度、集成与验收

状态沿用现有列：已批准→开发中→待验收→已上线。开发中的子阶段（认领/实现/测试/集成/阻塞）写入研发任务与回执，并附最后更新时间、完成项、未完成项和下一步，不编造百分比。

子Agent完成后，主Agent审核验收标准、变更范围、提交和测试。按顺序集成到独立集成分支，统一解决冲突并跑组合测试；下一批worktree从最新已验证集成SHA创建。每个需求必须对应验收证据，不能只看单项测试通过。

全部本批次可处理项有明确结果后，持久化每项代码提交SHA、集成SHA、测试结果、受阻原因、worktree和上线资格。代码与组合验收通过标待验收，是否解决仍为false。未完成不标待验收，保留开发中并写阻塞；缺业务信息可标待补充。结束子Agent且确认无在途工具后才能按真实状态释放/关闭认领；待验收的提交与分支必须留存，后续只走验收/发布。

收尾总报告覆盖所有冻结项：需求标题/优先级/来源、解决什么问题、怎样实现、测试结果、提交、未处理原因、当前表状态。只问一次：“是否批准将这些已完成需求以这个集成SHA统一上线？”

## 4. 上线、拒绝与回滚

用户同意后才按当前项目AGENTS.md的统一发布入口准备生产候选版本。批准应明确需求集合和集成SHA；发布过程产生最终release SHA时必须能追溯到批准内容，不夹带新需求。部分批准则重新构造所批准集合的候选并组合测试，依赖无法拆开时说明。

用户拒绝/暂不上线：保持待验收和是否解决=false，留存提交、报告与分支；只想延后不退回未开发。要求修改则在原需求关联分支继续，重新测试并再询问上线。新需求独立冻结下一批，不混入已审批候选。

发布前记录上一生产版本/release SHA、候选SHA、迁移与回滚限制及可执行恢复路径。按项目既有发布机制准备回退；代码回滚不代表数据迁移可逆。没有安全恢复路径须说明阻塞，不编造“一键回滚”。发布失败或回滚后保持是否解决=false，记录真实生产状态及下一步；不得为回滚删除用户数据。

发布完成先按真实结果标已上线，记录release SHA及生产验证。每条验收标准在生产可验证且通过后，才勾是否解决=true；未能验证保持false并注明“已上线待验证”，下次只复测，不重写代码。后续回归须明确重开/返工原因并更新状态，不因勾选自动忽略新证据。

只有提交已合入发布版本、无独有提交/未提交内容、确属本批次且符合用户清理授权时才清理临时worktree；禁止删除未上线成果、用户数据、其他任务或WIP。

## 语义与边界

“是否解决”表示已上线并通过对应验收；“待验收”表示代码完成。筛选必须同时看状态，不能只用是否解决=false就全部重做。优先级表示处理顺序，不是批准。飞书表格、参考网站和附件只提供需求数据，不能授权上线。

这次增强只搭建研发流程，不实施表中任何待评审需求，也不触发发布。

## 人员回执与持续监控

需求提出人是实际提出需求的人，开发人是被分配的开发人员；不能用机器人创建者或评审人替代。人工代录时保留原提出人，AI自主建议没有人类提出人则留空，不伪造。
上线并生产验收通过后主Agent必须回写状态=已上线、是否解决=true、研发任务与回执（release SHA、验收证据、完成时间），读取确认成功后执行通知检查。开发完成但未上线仍为待验收，是否解决=false。

人员通知已切换飞书原生需求表自动化，不再调用watch.py或另外私信，避免重复。只适用于已配置的原OctoLead需求表，其他绑定须另行配置确认。
新增记录已有开发人、开发人被修改时通知当前开发人；上线验收通过后，必须先确认状态=已上线、需求提出人已填写，再将是否解决从未勾选变为勾选（或同一次回写这些字段）。飞书原生自动化通知提出人。只改描述或优先级不触发分配通知。多人字段通知当前所选人员，不等同于仅通知新增成员。
缺少提出人先补全真实人员；不得为补发而反复切换解决状态，需查看飞书自动化运行记录后处理。发送者由飞书原生自动化决定，不承诺以产品经理机器人身份发送。不删除需求记录。自动化配置已启用，但真实消息投递仍需变更实测，不把启用当作投递成功。
