# 操作入口

> 先遵守 [配置与身份约定](context.md)。软件群任务使用注入配置和当前机器人；本页固定脚本、路径、群/表及身份仅是旧流程示例。只读查询不执行写入或调度流程。
所有命令在 `<TOOLS_ROOT>` 运行。运行时项目绑定从Bridge共享注册表读取；`product_manager/bindings.json`保留定时绑定名和enabled开关，不能猜ID。需求表URL：<CURRENT_GROUP_TABLE_URL>

- `python3 product_manager/runtime.py binding --binding octolead-rd`：检查机器人绑定。
- `python3 product_manager/runtime.py plan --binding octolead-rd`：读取全表及来源、优先级、状态。
- `python3 product_manager/runtime.py propose --binding octolead-rd --input 文件.json`：验证材料并创建待评审建议；重复key返回已有记录。
- `python3 product_manager/runtime.py report --binding octolead-rd --input 文件.json`：由产品经理向绑定群发送每日报告，输入`{"text":"实际报告"}`，默认同日不重复发送。用户明确要求额外手动测试/审查时，输入加稳定的report_id（如manual-review-20260909-01），与日报分开去重；同次重试沿用相同ID，不用新ID重发。

需求输入JSON：
```json
{"key":"稳定的场景障碍键，不含日期","title":"需求标题","priority":"中","user_scenario":"谁在何种场景做什么","evidence_type":"实测","evidence":"观察步骤、截图路径/资料来源；不写猜测为事实","outcome":"期望效果","acceptance":"能逐项验证的行为条件","priority_reason":"影响和证据，不编造工作量节约数字","proposal":"最小方案与范围","uncertainties":"未验证的假设，无则明确写无"}
```
`evidence_type`可选实测/用户反馈/假设待验证。脚本拒绝缺证据和验收条件；同日最多5条新建议。日期采用北京时间；创建超时保留pending账本，先查远端key再重试。人工直接填表不受AI建议新增上限限制。

# 给用户的填表方法
主要填：需求标题、用户与使用场景、期望结果、优先级。来源选人工；状态默认待评审。验收标准可先让产品经理补充，再由人评审。需求提出人和开发人使用真实人员字段。

# 产品→研发→测试
人明确批准具体record_id/需求链接后，将状态设为已批准，记录真实评审人，不从网页/机器人引用推断批准。研发读取已批准需求，再以独立worktree实现；状态开发中时必须把实际任务/分支及负责人写入研发任务与回执，防止多人重复认领。仅代码完成标待验收/尚未上线；用户批准且生产验证成功后才标已上线。测试把验收标准作为检查依据；失败的真实缺陷走现有巡检记录→人确认→Bug表，不再新建同义需求。
当前没有监听表格即时自动开工的服务；用户在群里@研发并指定已批准需求时执行。需要全天候自动认领时另行实现队列/锁和权限校验，不能将已批准字段称为自动开发触发器。

上面是定时/桌面命令。群内将 --binding octolead-rd 换为 --chat-id 真实群ID；话题另传 --topic-id 真实TopicID。未知绑定会拒绝。当前Topic发送尚未开放，不把群级消息称为Topic回执。


## 需求灵感来源（新增必填）
原“来源”仍表示人工/AI建议；新增“需求灵感来源”多选与“来源说明与引用”文本，记录想法从哪里来。propose新建时必须提供inspiration_sources与inspiration_details；旧需求幂等重试仍只返回原记录，不覆盖历史来源。
可选来源：实际体验、Bug表、巡检记录、人工需求/用户反馈、竞品对比、公开资料研究、方案探索。只勾真正启发该需求的来源，不能因去重时读过Bug表就把Bug表算来源。多个来源共同启发可多选；主来源在说明首句指出，辅助参考另列。
来源说明必须写具体记录链接/record_id、产品页面及操作场景、用户反馈出处或公开参考链接，并解释它如何导出此需求。无法追溯就明确缺失，不编造链接。仅有想法选方案探索，evidence_type仍标假设待验证；生成原型/设计验收不是自动证明需求存在。
示例字段：`"inspiration_sources":["实际体验","巡检记录"],"inspiration_details":"主要来自实际操作某页面的等待反馈；辅助依据为巡检记录的真实链接和现象。"`
群回执也简述灵感来源并附关键引用。既有同义需求补材料时维护真实来源，不能为新来源重建需求。新项目若缺这两列，先说明表结构不兼容，不静默丢弃来源。

### 来源必须具体到原始记录
来自Bug表或巡检记录的新需求，必须先读取真实原记录，再在payload提供inspiration_records数组。每项包含source（Bug表或巡检记录）、table_name（真实表名）、table_id、record_id、title（原记录标题）、url（含table与record的精确记录链接）、reason（原问题如何导出本需求）。脚本校验标识与链接一致并写入来源说明与引用；字段校验不代表已验证原记录存在，Agent必须实际读取原记录。多条依据逐条列出，不能只有表的首页链接或类别名称。
实际体验要写“来源表：无（直接体验）”，记录真实页面、步骤、现象、截图；公开资料写具体文章标题、链接、借鉴点。没有真实表记录不能编成Bug表或巡检表来源；只读某表去重不是灵感来源。旧需求没有证据的部分明确记“缺失”，不能补造。

## 提出来源标注
需求表的「提出来源」为单选：人工 / AI，人工新增默认人工。Agent自主体验、分析或竞品对比后提出的需求必须写入「AI」，runtime.py propose 自动填入。人提出、Agent仅整理或代录的需求仍为「人工」，不要通过自主提案入口代录；人工评审或批准不改变来源。既有需求补充材料保留原提出来源。「需求灵感来源」及「来源说明与引用」继续记录具体依据。旧「来源」列保留用于兼容现有脚本，主视图展示「提出来源」。
